# 社内問合せAIチャットボットアプリ

## アプリ概要

本アプリは、人事総務・経理・法務・IT部門（情シス）を想定した  
**社内問い合わせ向けAIチャットボット（RAG構成）** です。

- 社内規程・マニュアルをもとに回答を生成
- 管理者モードからナレッジ（ドキュメント）を管理可能
- 管理者には部門ロールを付与し、自部門のドキュメントのみ操作可能
- 誤回答を防ぐため、業務判定・部門判定・検索強度判定を段階的に実施

## LLM プロンプト設計

LLM には以下3種類の役割を持たせています。

1. **業務判定**
   - 社内業務に関係する質問かどうかを判定
2. **部門判定**
   - DBに登録された部門コードをもとに primary / secondary を判定
3. **回答生成**
   - 検索結果チャンクと会話履歴のみを根拠に回答

## FAISS と DB の役割分担

- **PostgreSQL**
  - ドキュメント・チャンク・ユーザ・権限・操作ログ
  - キーワード検索（LIKE / full-text 相当）

- **FAISS**
  - 類似検索専用インデックス
  - index.write / read によりファイルとして永続化

検索インデックスとデータストアを分離することで、  
再構築・差し替えが容易な構成としています。

## データモデル設計の考え方

本アプリでは、RAG構成と業務ログの両立を意識し、  
以下の方針でモデルを分離しています。

### Department

- 部門単位でドキュメント・検索スコープ・権限を制御
- RAG検索時のフィルタリング軸として使用

### Document

- アップロードされた元ファイル単位の管理
- 「誰が・どの部門で・いつ登録したか」を追跡可能

### Chunk（RAGの中心）

- RAG検索の最小単位
- Document とは独立させ、検索・出典表示・検証を容易にする設計
- embedding は検索用途、content は生成用途として分離

### ChatSession / ChatMessage

- 会話履歴を UI 状態ではなく **業務ログ** として管理(検索メタ、RAGメタも残す)
- 分析・品質改善を前提とした設計
  - 評価ボタンを配置することでユーザのフィードバックをログとして残す
  - 評価ログに紐づくアシスタントメッセージのメタ情報を確認し、分析・品質改善の情報として残す

### AuditLog

- ドキュメント操作（アップロード / 削除）を記録
- 「誰が・何を・どの部門で行ったか」を追跡可能
- 今後の拡張機能に応じて、監査項目の追加も検討可能(例：OCRの読み込み結果等)

## セッションと会話管理

- ユーザごとに複数の ChatSession を保持
- 各セッションから直近 N 件の履歴を取得して LLM に渡す
- 会話履歴を業務ログとして扱える構成(メタ情報やFBを保持)

---

## ユーザ質問から RAG 回答までのフロー

1. ユーザ入力を受信（ChatSession 付き）
2. 直近の会話履歴を取得し、`session_context` を生成
3. ルーティング分類器で業務判定・部門判定を実施
4. 業務外の場合は即時リターン
5. フォローアップ判定を行い、検索クエリを補正
6. クエリを埋め込み化
7. HybridRetriever に検索を依頼
   - 部門スコープ → 全社フォールバック
8. 検索弱時は **hard clarification** を返却
9. 根拠が十分な場合のみ回答生成
10. 必要に応じて **soft clarification** を付与
11. 回答・メタ情報・出典を返却

---

## 設計上の考慮点（RAG）

本アプリでは、

「正確に答える」よりも「誤って答えない」ことを重視

しています。

- 業務外質問は早期に除外
- 部門・前提が曖昧な場合は即答しない
- 検索結果が弱い場合は回答を返さない
- 根拠が十分な場合のみ回答を確定

---

## Clarification（聞き返し）設計

- **Hard clarification**
  - 回答生成せず、追加情報を要求
  - 誤回答防止を最優先

- **Soft clarification**
  - 回答後に条件確認を1問だけ付与
  - UX を損なわず安全性を確保

---

## routing_meta / retrieval_meta

各回答には以下のメタ情報を保存しています。

- routing_meta
  - 業務判定・部門判定・clarification 要否
- retrieval_meta
  - 検索方式・ヒット数・スコープ・フォールバック有無

これらは **検証・デバッグ・品質改善** を目的としています。
